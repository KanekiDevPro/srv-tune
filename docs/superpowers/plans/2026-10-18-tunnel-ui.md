# Tunnel UI implementation plan

**Goal:** give `vpn-tunnel` operators a TUI and a loopback-bound web panel
over one shared bash core: tunnel status, key lifecycle, sessions, and
guarded sshd access-policy edits.

**Architecture:** all logic in `lib/tunnel.sh`. `srv-tune tunnel ...` is a
thin dispatcher over it. The web panel is a single python3-stdlib file that
shells out to the CLI with `--json` and never re-implements tunnel logic.

**tech stack:** bash 5, bats-core, python3 standard library only. No new
runtime dependencies.

**Spec:** `docs/superpowers/specs/2026-10-18-tunnel-ui-design.md`

**Branch:** `v0.3/tunnel-ui` (already pushed with the spec commit).

> Executor: use `superpowers:executing-plans` (or
> `subagent-driven-development` if the user chose it). Work top to bottom,
> one commit per task. Linux is the test source of truth (Windows dev hosts
> time out on the full suite).

## Global contracts (read before Task 1)

### Environment

| Variable | Meaning | Default |
|---|---|---|
| `SRV_TUNE_TUNNEL_USER` | tunnel account | `tunnel` |
| `SRV_TUNE_TUNNEL_HOME` | override home dir (tests) | `getent passwd` field 6 |
| `SRV_TUNE_SS_BIN` | `ss` binary override (tests) | `ss` |
| `SRV_TUNE_BIN` | CLI the web panel calls | `srv-tune` |
| `SRV_TUNE_ACTOR` | audit actor: `cli` / `tui` / `web` | `cli` |
| `SRV_TUNE_SRC` | audit source: tty path or remote IP | `$(tty)` or `cli` |
| `SRV_TUNE_TEST=1` | sandbox mode: bypass root gates, skip daemons | unset |
| `SRV_TUNE_SYSROOT` | path prefix for system files (tests) | `/` |

Root gates read `is_root` from `lib/util.sh`. Rule everywhere: mutation
requires root **unless** `SRV_TUNE_TEST=1` (unit tests run unprivileged in
CI; the TEST bypass must carry a comment).

### lib/tunnel.sh function table

| Function | Output / behavior |
|---|---|
| `tunnel_dropin` | `ssh_dropin_path` (sources `modules/ssh.sh` via `module_load ssh`) |
| `tunnel_mode` | `TUNNEL` \| `ADMIN` \| `CUSTOM` \| `absent` from line 1 of the drop-in |
| `tunnel_port` | first `Port` value in the drop-in, else `22` |
| `tunnel_user` | first `Match User` value, else `SRV_TUNE_TUNNEL_USER`/`tunnel` |
| `tunnel_permit_open` | indented `PermitOpen` value, else `none` |
| `tunnel_gateway_ports` | `yes`/`no` from the drop-in, else `no` |
| `tunnel_permit_tunnel` | `yes`/`no` from the drop-in, else `no` |
| `tunnel_ip_forward` | `yes` when `$(sys_p /etc/sysctl.d/00-srv-tune-tun.conf)` contains `net.ipv4.ip_forward=1` |
| `tunnel_status_text` | `key: value` lines, one per line (pipeable) |
| `tunnel_status_json` | single-line JSON object |
| `tunnel_sessions_text` | `peer pid=N` lines |
| `tunnel_sessions_json` | `{"sessions":[{"peer":"...","pid":"..."}]}` |
| `tunnel_keys_text` | `SHA256:... TYPE comment` lines |
| `tunnel_keys_json` | `{"keys":[{"fp":"...","type":"...","comment":"..."}]}` |
| `tunnel_audit <action> <fp> <comment> <result>` | append to `$(state_effective_dir)/tunnel-actions.log`, mode 600 |
| `tunnel_main <args...>` | dispatch: no args → TUI; `status`,`keys`,`access`,`sessions`,`web` |

Exit codes: `0` ok, `1` runtime failure, `2` usage/precondition.

### Status text (exact line order)

```
mode: TUNNEL
port: 22
user: tunnel
permit_open: none
gateway_ports: no
permit_tunnel: no
ip_forward: no
dropin: /etc/ssh/sshd_config.d/00-srv-tune.conf (present)
sessions: 2
```

`sessions` is `unavailable` when `ss` is missing and no `SRV_TUNE_SS_BIN`
is set. Drop-in suffix is `(present)` or `(absent)`.

### Status JSON (keys always present)

```json
{"mode":"TUNNEL","port":"22","user":"tunnel","permit_open":"none","gateway_ports":false,"permit_tunnel":false,"ip_forward":false,"dropin":"/etc/ssh/sshd_config.d/00-srv-tune.conf","dropin_present":true,"sessions":0}
```

`sessions` is `null` when unavailable. JSON string values escape `\` and
`"`; all reflected values are already restricted (port numeric, user from
`Match User`, permit_open validated on write).

### Audit line

```
ts=<ISO-8601> actor=cli action=key-add fp=SHA256:... comment="laptop" src=/dev/pts/1 result=ok
```

## Task 2 — key lifecycle

**Files:** `lib/tunnel.sh`, `tests/test_tunnel.bats`

**Contract:**

```
srv-tune tunnel keys list [--json]
srv-tune tunnel keys add [--file PATH|-] [--comment TEXT]   # stdin when no --file
srv-tune tunnel keys remove --fp SHA256:...
```

- Root or `SRV_TUNE_TEST=1` required for `add`/`remove`.
- `tunnel_home`: `SRV_TUNE_TUNNEL_HOME` if set; else `getent passwd "$user"`
  field 6; else print `error: tunnel user X does not exist (apply the
  vpn-tunnel profile first)` and return 2.
- `add`: read exactly one non-empty key line (trim CR/LF); multiple
  non-empty lines → error 1. Validate with `ssh-keygen -lf <tmp>` (0600,
  removed after). Dedupe by key body (base64 field) against existing lines;
  duplicate → `error: key already present (SHA256:...)`, exit 1.
- `--comment` replaces the trailing comment in the stored line; no
  `--comment` stores the line as given. Options before the key type
  (`restrict,permitopen="..."`) are preserved.
- Mutation steps, in order: resolve home → validate → `new_backup_id` →
  `backup_file "$keys" "$state/backups/keys-<id>"` → write temp in the
  same dir (mode 600) → `mv` → `chmod 700` dir, `chmod 600` file →
  `chown "$user:$user"` when root → audit → print
  `added SHA256:... (comment)`.
- `remove`: rebuild the file by fingerprint using per-line temp files;
  missing fp → error 1 and no write. Audit result `ok`/`fail` (fail lines
  are appended for rejected adds too, best effort).
- Audit writes are best effort: warn on failure, never change the exit code.
- Keys JSON: `{"keys":[{"fp":"SHA256:...","type":"ED25519","comment":"laptop"}]}`
  (`ssh-keygen -lf` parsing: bits, fp, comment, type; trim trailing space).

**Tests (append).** Never hardcode a key literal: generate a real key so
`ssh-keygen -l` accepts it, and skip when `ssh-keygen` is absent.

```bash
_tunnel_keygen() {
  command -v ssh-keygen >/dev/null 2>&1 || skip "ssh-keygen not installed"
  ssh-keygen -q -t ed25519 -N '' -f "$SRV_TUNE_TMP/id_test" >/dev/null
  KEY="$(cat "$SRV_TUNE_TMP/id_test.pub")"
}

@test "tunnel keys add from stdin stores the key with safe perms" {
  _tunnel_setup
  _tunnel_keygen
  run bash "$SRV_TUNE_ROOT/optimizer.sh" tunnel keys add --comment laptop <<<"$KEY"

  grep -q 'laptop' "$f"
  [ "$(stat -c '%a' "$f")" = "600" ]
  [ "$(stat -c '%a' "$(dirname "$f")")" = "700" ]
  ls "$SRV_TUNE_STATE_DIR"/backups/keys-* >/dev/null
  grep -q 'action=key-add' "$SRV_TUNE_STATE_DIR/tunnel-actions.log"
}

@test "tunnel keys add --comment replaces the trailing comment" {
  _tunnel_setup

  _tunnel_setup
  _tunnel_keygen

  fp="$(ssh-keygen -lf "$SRV_TUNE_TUNNEL_HOME/.ssh/authorized_keys" | awk '{print $2}')"
```

## Task 4 — access show / set

**Files:** `lib/tunnel.sh`, `tests/test_tunnel.bats`

**Contract:**

```
srv-tune tunnel access show [--json]
srv-tune tunnel access set --permit-open LIST --gateway-ports yes|no [--yes]
```

- `show`: `mode`, `permit_open`, `gateway_ports`, `permit_tunnel` (text
  `key: value`, JSON object). No root needed.
- `set`:
  - Require root unless `SRV_TUNE_TEST=1`.
  - Require `mode == TUNNEL`; otherwise
    `error: not a tunnel server (apply --profile vpn-tunnel --with-ssh first)`,
    exit 2.
  - Both flags required; missing → usage, exit 2.
  - Validate `--permit-open`: `none` or comma-separated `host:port` with
    `host` matching `[A-Za-z0-9.*_-]+` and `port` 1-65535; invalid → exit 2.
  - Preserve what the operator already has: detect current user, port,
    `PermitTunnel` (`yes` → export `SRV_TUNE_TUNNEL_MODE=tun`), so the
    re-render cannot silently disable tun forwarding.
  - Ask for typed `SSH-YES` via `ui_type_confirm` unless `--yes` (which
    sets `SRV_TUNE_ASSUME_YES=1`). Print the lockout risk first.
  - Acquire the existing operation lock (`source lib/lock.sh`;
    `lock_acquire` before `run_apply`, `lock_release` on every path) so a
    concurrent apply cannot write the drop-in underneath this edit.
  - Export `SRV_TUNE_SSH_MODE=TUNNEL`, `SRV_TUNE_TUNNEL_USER`,
    `SRV_TUNE_SSH_PORT`, `SRV_TUNE_PERMIT_OPEN`,
    `SRV_TUNE_TUNNEL_GATEWAY=0|1`, `SRV_TUNE_PROFILE=vpn-tunnel`, then call
    `run_apply vpn-tunnel ssh` (from `lib/modules.sh`). Do not touch the
    drop-in directly: `ssh_apply` already backs up, validates, arms the
    guard, reloads, verifies, and prints `guard <id> armed`.
  - `run_apply` re-asks the dangerous-module confirmation; the exported
    `SRV_TUNE_ASSUME_YES=1` is the explicit opt-in after our own typed
    confirm.
  - Exit with `run_apply`'s status; pass its output through unchanged.
- Tests (SYSROOT + `SRV_TUNE_TEST=1`, stubs copied from `test_ssh.bats`:
  `SRV_TUNE_SSHD_BIN`, `SRV_TUNE_SS_BIN`, `SRV_TUNE_NO_GUARD=1`):


## Risks the executor must not paper over

- Root HTTP server is the main new attack surface: keep it loopback by
  default, token 600, POST+CSRF, and the minimal endpoint set. Do not "fix"
  a failing web test by loosening auth.
- `access set` must preserve the current port/user/tun knob; losing them
  silently changes the server's network exposure.
- `ssh-keygen -l` is the only key validator used; do not hand-roll base64
  parsing beyond locating the key body for dedupe.
